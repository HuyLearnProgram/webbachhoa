# Bách Hóa E-commerce — Frontend (client)

## Tổng quan

Frontend React cho website thương mại điện tử bách hóa (Vietnamese grocery e-commerce). Kiến trúc SOA/REST: frontend này giao tiếp với backend Spring Boot nằm ở `../server` qua RESTful API. Repo: https://github.com/HuyLearnProgram/webbachhoa

## Tech stack

- **React 18** + **Vite** (JS thuần, không TypeScript). Alias `@/* → src/*` (xem `jsconfig.json`).
- **State**: Redux Toolkit + `redux-persist` (persist vào `localStorage`, key `ogani_shop/user`, whitelist `isLoggedIn/token/current`), có `<PersistGate>` bọc app trong `main.jsx`.
- **Routing**: `react-router-dom` v6, 3 layout lồng nhau — `Public`, `MemberLayout`, `Admin`.
- **HTTP**: một `axiosInstance` dùng chung (`src/utils/axios.js`).
- **UI**: Tailwind CSS (trang khách hàng) + Ant Design (chủ yếu trang admin) + styled-components.
- **Khác**: `react-hook-form`, `chart.js`/`react-chartjs-2` (dashboard doanh thu), `html2canvas` + `jspdf` (xuất hóa đơn PDF admin), `sweetalert2`, `react-toastify`, `@react-oauth/google` (hiện đang tắt).

## Routing & phân quyền

- `Public` layout: trang khách (chưa đăng nhập) — Home, danh sách/chi tiết sản phẩm, giỏ hàng, checkout, kết quả thanh toán.
- `MemberLayout`: guard tự viết ngay trong component — redirect `/login` nếu `!isLoggedIn`.
- `Admin` (`src/pages/admin/Admin.jsx`): guard tự viết trong `useEffect`, đọc `state.user`, redirect `/login` nếu chưa đăng nhập, redirect `/` nếu `role.roleName !== 'admin'`. **Không có** HOC/route-guard tái sử dụng chung (`src/hocs/` chỉ có `withBaseComponent.jsx`, không liên quan auth).

## State management

- **`app` slice**: `categories` (load 1 lần khi `App.jsx` mount qua thunk `getCategories()`), `isLoading`, `isShowModal` + `modalChildren` (điều khiển modal toàn cục qua component `Modal.jsx`), `errorCode`.
- **`user` slice**: `isLoggedIn`, `current` (user hiện tại, gồm `cartLength`), `token`, `message` (dùng cho thông báo hết phiên — `setExpiredMessage()`).

## API layer

- `src/utils/axios.js`: 1 `axiosInstance` (`baseURL = VITE_BACKEND_URL`). Request interceptor đọc JWT trực tiếp từ `localStorage['persist:ogani_shop/user']` để gắn `Authorization`. Response interceptor tự refresh token khi 401 qua `GET /auth/refresh`, gộp các lần refresh đồng thời qua biến `refreshPromise` (đã xử lý xong, xem lịch sử bên dưới).
- `src/apis/{app,category,location,order,product,user}.js`: các hàm gọi API theo domain. `location.js` gọi thẳng API công khai bên ngoài (esgoo.net) cho tỉnh/huyện/xã, không qua `axiosInstance`.

## Tích hợp đáng chú ý

- **VNPay**: `Checkout.jsx` redirect sang trang thanh toán VNPay, lưu tạm dữ liệu đơn vào `localStorage` để trang callback (`PaymentSuccess.jsx`) hoàn tất (cập nhật tồn kho, xoá giỏ hàng, gửi email).
- **Voucher giảm giá**: xử lý inline trong `Checkout.jsx` (`apiGetMyVouchers`, tính % hoặc số tiền cố định).
- **Đánh giá sản phẩm**: `apiRatings`/`apiGetRatingsPage`, hiển thị qua `Votebar`, `Comment`, modal `VoteOption`.
- **Ảnh sản phẩm/avatar**: phục vụ từ storage của backend (`VITE_BACKEND_TARGET/storage/...`), README nhắc Cloudinary nhưng thực tế chưa thấy tích hợp SDK Cloudinary trong `src/`.

## Lịch sử các phần đã hoàn thành (tóm tắt)

Các mục dưới đây **đã xử lý xong và xác nhận qua test**, không cần xem xét lại — chỉ giữ tóm tắt để biết bối cảnh, không đi sâu chi tiết.

- **Cơ chế refresh token** — 4 lỗi chồng lên nhau (biến `state` undefined trong `axios.js`, dùng sai axios instance khi retry, backend không bao giờ trả 401 do thiếu `CustomAuthenticationEntryPoint`, race condition khi nhiều request cùng gọi `/auth/refresh`) đều đã sửa. *Quyết định*: sửa backend trả đúng 401 thay vì vá frontend coi 403 như 401, để giữ đúng ngữ nghĩa REST (401 = chưa xác thực, 403 = thiếu quyền).
- **PersistGate** — thiếu `<PersistGate>` gây flash sai trạng thái đăng nhập + đá nhầm về `/login` khi F5 trang member. Đã thêm vào `main.jsx`.
- **Thunk `getCurrentUser`** — dùng sai `isRejectedWithValue` (type-guard) thay vì `rejectWithValue` (từ `thunkAPI`) khiến thunk không bao giờ reject đúng khi lỗi. Đã sửa.
- **Dọn code chết/cấu hình sai**: route `Feedback` trùng lồng trong `App.jsx` (không thể tới được, đã xoá) · `package.json` xoá `"client": "file:"`, `"npm"`, `"i"` (dependency thừa/cài nhầm), `vite-jsconfig-paths` chỉ giữ ở `devDependencies` · `ProviderWrapper.jsx` chuyển từ `src/store/` sang thư mục test (chỉ dùng cho `Checkout.test.jsx`) · đã thêm `.env.example`.
- **Quản lý người dùng (User) trong admin** — xây mới hoàn chỉnh: trang Edit User (`EditUser.jsx` + `EditUserForm.jsx`), tìm kiếm/lọc trong `User.jsx` (sửa 2 lỗi ẩn: thiếu `paramsSerializer` ở frontend + `UserService.fetchAllUser()` bỏ quên tham số `Specification` ở backend), email thông báo tự động khi admin sửa thông tin/khoá tài khoản (phân biệt rõ với user tự sửa qua `SecurityUtil.getCurrentUserLogin()`), bắt buộc chọn lý do khi khoá tài khoản, chặn admin tự khoá chính mình, polish layout form + nút "Quay về" (`TurnBackHeader.jsx`, dùng chung 6 trang admin). *Quyết định*: bỏ hẳn chức năng Xoá cứng user (rủi ro vỡ ràng buộc khoá ngoại với đơn hàng/đánh giá vì không có `cascade`, dùng Khoá/Active thay thế); chọn gửi email minh bạch-sau-khi-sửa thay vì audit log (chỉ truy vết được sau sự việc) hoặc cơ chế xin-phép-trước qua toggle (có lỗi logic con-gà-quả-trứng: user cần admin sửa giúp nhiều nhất chính là lúc họ không tự bật được toggle đó).
- **Lỗ hổng Broken Access Control ở `/api/v2/users/**`** — mọi endpoint của `UserController` (list, get by id, create, update, delete) trước đó chỉ yêu cầu "đã đăng nhập" (`anyRequest().authenticated()`), không phân biệt role, nên 1 khách hàng thường có thể tự gọi API để sửa/khoá tài khoản người khác. Đã sửa: `SecurityConfiguration.java` thêm `hasRole("ADMIN")` cho `GET/POST/PUT /users` và `DELETE /users/**`; riêng `GET /users/{id}` giữ `authenticated()` (vì `Personal.jsx`/`Checkout.jsx`/`MemberSidebar.jsx` cũng gọi endpoint này để tự xem hồ sơ của chính mình) và thêm kiểm tra "chính chủ HOẶC admin" ngay trong `UserController.getUser()`. *Lưu ý kỹ thuật quan trọng*: `SecurityUtil.getUserRole()`/`getUserId()` đã có sẵn nhưng **chết** (giả định principal là `Jwt`, trong khi `JwtAuthenticationFilter` đang dùng thực tế set principal là `String`) — không dùng 2 hàm này, phải đọc role qua `SecurityContextHolder...getAuthorities()`.
- **Đăng ký tài khoản mới tự động thành ADMIN (Critical — Privilege Escalation)** — `AuthController.register()` hard-code `Role r; r.setId(2)` (2 = ADMIN theo seed SQL) cho mọi tài khoản tự đăng ký, thay vì `1` (USER). Đã sửa tận gốc bằng cách đổi endpoint từ nhận thẳng `@RequestBody User` (JPA entity, có thể bị mass-assignment field `id`/`role`/`status` từ client) sang 1 DTO input riêng `RegisterRequestDTO` (chỉ `name`/`email`/`password`, có validate `@Email`/`@Size(min=6)`) — controller tự dựng `User` mới và luôn gán role id=1. Tiện thể vá thêm: `UserService.create()` bắt `DataIntegrityViolationException` khi 2 request đăng ký trùng email gần như đồng thời (trước đó rơi vào handler chung, trả 500 kèm message lỗi SQL thô) → trả 400 thân thiện. *Quyết định*: không chỉ đổi `2` thành `1` mà đổi hẳn sang DTO, vì bind thẳng entity còn hở khả năng client tự gửi `id` để `save()` chạy `merge()` đè lên user khác (chưa kiểm chứng thực nghiệm nhưng đủ rủi ro để đóng luôn bằng cấu trúc thay vì chỉ sửa giá trị). Không đụng `UserController.createNewUser()` (`POST /users`, cùng kiểu bind entity) vì đã bị khoá `hasRole("ADMIN")` từ lần sửa trước, rủi ro thấp hơn nhiều.
- **Trang admin "Xem chi tiết người dùng"** (`UserDetail.jsx`, route `/admin/user/detail/:userId`) — xây mới: thông tin cơ bản read-only (kèm nguồn đăng nhập Local/Google, thêm field `provider`/`providerId` vào `UserDTO`), 4 số liệu tổng hợp (tổng đơn/tổng chi tiêu/số feedback/rating TB, tính client-side từ dữ liệu đã fetch), 2 tab Đơn hàng/Đánh giá (mặc định tab Đơn hàng) có filter+search riêng, nút Sửa/Khoá-Mở khoá ngay trên trang (tái dùng state machine lý do khoá từ `User.jsx`). Backend thêm 2 endpoint mới `GET users/{id}/orders` (tái dùng query `findOrdersWithOptionalStatus` có sẵn, vốn chỉ dùng cho self-service `/orders`) và `GET users/{id}/feedbacks` (mirror `getByProductId`), cả 2 dùng "auto full-size khi không truyền `size`" (trick có sẵn ở `FeedbackController.getByProductId`) để trả hết dữ liệu 1 lần, tính tổng/trung bình ở frontend, không cần thêm aggregate query. *Lỗ hổng phát hiện kèm, đã vá luôn*: `GET /api/v2/allOrders` (dùng ở `Order.jsx` admin) trước đó không có `hasRole("ADMIN")`, cùng loại Broken Access Control đã sửa cho `/users` — đã thêm rule, xác nhận qua grep không có luồng khách hàng nào gọi `apiGetAllOrders`.
- **Tính đúng "Tổng chi tiêu"/doanh thu — thêm trạng thái thanh toán thật cho Order** — phát hiện gốc rễ: hệ thống trước đó không có cách nào biết 1 đơn VNPay đã thực sự được thanh toán hay chưa (`Order` không có field `paymentStatus`, `status` 0-3 chỉ là trạng thái vận chuyển; callback VNPay chỉ đọc `vnp_ResponseCode` rồi redirect, không verify chữ ký, không cập nhật `Order`; `vnp_TxnRef` sinh ngẫu nhiên không gắn với `orderId` nên không đối chiếu được). Đã xây state machine `paymentStatus` mới trên `Order` (`UNPAID`/`PENDING_PAYMENT`/`PAID`/`PAYMENT_FAILED`/`REFUND_PENDING`/`REFUNDED`) + field `vnpTxnRef`/`transactionNo`/`paidAt`: COD → `PAID` tự động khi giao thành công (`status=2`); VNPay → `PaymentService.confirmVnPayCallback()` verify HMAC-SHA512 chữ ký (tái dùng `VNPayUtil.hmacSHA512`/`getPaymentURL` có sẵn) + đối chiếu đúng `Order` qua `vnp_TxnRef` (gắn `orderId` vào lúc tạo link thanh toán) + so khớp số tiền chống giả mạo, mới set `PAID`; huỷ đơn đã `PAID` → `REFUND_PENDING` (endpoint mới `GET orders/{id}/confirm-refund`, admin xác nhận thủ công sau khi hoàn tiền ngoài hệ thống). Công thức cuối cùng: `Σ total_price WHERE paymentStatus='PAID'` — duy nhất, đúng theo cấu trúc, tự loại mọi trường hợp chưa/thất bại/đang-đã hoàn tiền. Tiện thể chuyển `vnp_TmnCode`/`secretKey` từ hard-code sang `application.properties` (`@Value`) vì phát hiện tài khoản sandbox cũ đã bị VNPay từ chối ("Website chưa được phê duyệt") — người dùng tự đăng ký tài khoản sandbox mới và cập nhật. *Quyết định*: dữ liệu VNPay cũ không có bằng chứng giao dịch (không lưu `vnp_TxnRef`) nên backfill xấp xỉ `status≠Cancelled → PAID` (xem `SQL/backfill_payment_status.sql`, chạy 1 lần) — chấp nhận không chính xác 100% cho lịch sử, đơn mới tạo sau khi triển khai chính xác tuyệt đối. Không tự động gọi API refund thật của VNPay (tích hợp riêng lớn hơn, ngoài phạm vi) — chỉ dừng ở đánh dấu trạng thái để admin xử lý hoàn tiền thủ công.
- **Bug bọc lồng response ở `POST /checkout`** — phát hiện khi test luồng VNPay thật: `FormatResponse.java` (`ResponseBodyAdvice` toàn cục) đã tự bọc **mọi** response thành công (status &lt; 400) vào `RestResponse{statusCode, data, message}`, nhưng `OrderController.create()` lại tự tay bọc thêm 1 lớp `RestResponse<Long>` nữa trước khi trả về → JSON cuối cùng bị lồng 2 lớp, khiến `response.data` ở frontend không phải là `orderId` mà là cả object lồng bên trong (gây lỗi `net::ERR_FAILED` khi nhét nguyên object đó vào query string gửi sang VNPay). Đã sửa: nhánh thành công trả thẳng `order.getId()` (raw `Long`), để `FormatResponse` tự bọc đúng 1 lần — khớp convention mọi endpoint khác trong dự án (VD `UserController.getUser()`). Nhánh lỗi giữ nguyên (không bị ảnh hưởng vì `FormatResponse` chủ động bỏ qua khi status ≥ 400). Đã sửa tương tự cho `confirmRefund()`. *Lưu ý kỹ thuật quan trọng*: bug này là **pattern chung**, có thể còn ẩn ở các endpoint khác tự tay bọc `RestResponse` ở nhánh thành công (VD `updateOrderStatus()` — chưa sửa vì frontend hiện chỉ đọc `statusCode`, không đọc `data`, nên chưa lộ bug; cần lưu ý nếu sau này có chỗ đọc `.data` của response từ các endpoint dạng này).
- **Tính năng "Trả hàng hoàn tiền" sau khi giao thành công** — site đã quảng cáo sẵn "Trả hàng miễn phí 15 ngày" (`OrderCard.jsx`, `constants.jsx`) nhưng chưa có backing (`isValidStatusTransition` coi `status=2` Succeed là trạng thái cuối, không có đường trả hàng). Đã thêm `status=4` "Returned" — khách hàng (chủ đơn) hoặc admin gọi lại đúng endpoint `updateOrderStatus` sẵn có (không cần endpoint mới) để chuyển `2→4`, kèm validate mới: phải `paymentStatus=PAID`, còn trong hạn 15 ngày kể từ `deliveryTime` (admin được bỏ qua hạn này), và phải là chủ đơn hoặc admin (thêm check ownership qua `SecurityUtil.getCurrentUserLogin()`, throw `PermissionException` → 403 nếu sai). Khi chuyển sang `status=4` và đơn đang `PAID`, tự động set `paymentStatus=REFUND_PENDING`, tái dùng nguyên xi cơ chế `REFUND_PENDING→REFUNDED` (nút "Đánh dấu đã hoàn tiền") đã xây cho huỷ đơn — không cần thêm gì ở đây. *Quyết định*: không có bước admin duyệt/từ chối trước khi chuyển `status=4` — khách bấm là chuyển ngay, giống hệt cơ chế Huỷ đơn hiện có, đúng mức độ đơn giản người dùng yêu cầu. API `/orders` (khách hàng) trước đó không trả `deliveryTime`/`paymentStatus` — đã bổ sung vào `OrderDetailDTO`/`OrderService.getOrderByCurrentUser()` vì khách cần biết hạn 15 ngày còn lại. Sửa kèm "Tổng lợi nhuận" ở Overview admin: `OrderService.getOverviewStats()` trước đó tính theo `sumTotalPriceByStatus(2)` (status vận chuyển, không biết gì về hoàn tiền) → đổi sang `sumTotalPriceByPaymentStatus("PAID")` (thêm query mới `OrderRepository`), tự động trừ đúng khi có đơn `REFUND_PENDING`/`REFUNDED`.
- **Polish sau khi test tính năng Trả hàng hoàn tiền** — vá bug `OrderService.findOrder()` thiếu `paymentStatus` (method xây `OrderDTO` riêng biệt, tách khỏi `convertToOrderDTO()`, bị sót khi thêm field); gộp 3 nút nổi ở `OrderDetail.jsx` admin (Cập nhật giao hàng/In hóa đơn/Đánh dấu đã hoàn tiền) vào 1 container `flex-column` chung + chống bấm đúp (`isRefunding`); `UserDetail.jsx` thêm lọc `paymentStatus` + sắp xếp đơn hàng; sửa nhãn "Default" → text ngữ cảnh ở các Select filter dùng `value` controlled. *Lưu ý kỹ thuật*: dự án có nhiều chỗ tự xây `OrderDTO` thủ công (`findOrder`, `convertToOrderDTO`, `cancelOrder`...) thay vì dùng chung 1 hàm convert — thêm field mới cần rà lại tất cả các nơi này.

Nghiên cứu Shopify/WooCommerce/Haravan/Sapo/KiotViet, đã lọc theo quy mô dự án — SKU/barcode nâng cao, giá vốn, hạn sử dụng (đặc thù grocery) vẫn **chủ động không làm** (effort cao/lợi ích thấp so với quy mô dự án); riêng khuyến mãi có ngày hết hạn **đã làm ở Giai đoạn 3** theo yêu cầu mới, đảo ngược quyết định ban đầu.

**Đã hoàn thành toàn bộ** — không còn việc nào dang dở cho trang Product admin. Riêng tab "Đơn hàng chứa sản phẩm" ở trang chi tiết (backend chưa có endpoint truy vấn `OrderDetail` theo `productId`) chủ động không xây vì không nằm trong yêu cầu, xem thêm ở "Vấn đề còn lại" nếu cần làm sau. **Cần làm tiếp**: kiểm tra tay qua trình duyệt thật (UI của box/badge/modal khuyến mãi mới chỉ xác nhận qua API + code review, xem mục Giai đoạn 3 ở trên).

## Vấn đề còn lại — bước tiếp theo

**Tạm hoãn, chờ giải pháp thay thế (người dùng chủ động chọn không vá code cũ):**
1. `apiGetRecommendedProducts` (`src/apis/product.js`) gọi `axiosInstanceRecommended` không tồn tại — tính năng gợi ý sản phẩm gãy hoàn toàn.
2. Google OAuth login đã viết (`GoogleLogin`, `apiLoginGoogle`) nhưng bị comment out trong `Login.jsx`.
3. Đăng ký tài khoản chưa xác thực email bằng OTP — hiện ai điền email nào cũng đăng ký được ngay, không cần chứng minh sở hữu email đó. Gộp chung nhóm "tạm hoãn" với Google login vì cùng là mở rộng luồng đăng ký/đăng nhập.

**Nợ kỹ thuật nhỏ từ trang User admin (chưa xử lý):**
3. `EditUserForm.jsx`: `initialUserData` là snapshot đông cứng lúc mount, không cập nhật sau khi lưu — hiếm khi gây sai nếu lưu nhiều lần liên tiếp không rời trang.
4. `EditUserForm.jsx` chưa có chức năng đổi avatar (chỉ xem) — **chủ động không làm theo yêu cầu người dùng**.

**Đã test xong** (không cần xem lại): backfill `payment_status` dữ liệu cũ, thanh toán VNPay sandbox thật thành công (`paymentStatus` chuyển đúng `PAID` qua callback đã verify chữ ký), toàn bộ luồng + test biên Trả hàng hoàn tiền (xem mục "Test biên luồng Trả hàng hoàn tiền" ở lịch sử phía trên), luồng search mới ở `Order.jsx`/`Feedback.jsx`, ownership check mới của `updateOrderStatus`.

**Tạm hoãn theo yêu cầu người dùng:**
5. Sửa stored procedure `GetRevenueByWeekCycle` (biểu đồ doanh thu tuần, `GET /monthly-orders-revenue`) — đã xác nhận qua `SHOW CREATE PROCEDURE` là nó cộng dồn **toàn bộ** đơn hàng theo `order_time`, không lọc `status`/`payment_status` gì cả (bug nặng hơn cả `getOverviewStats()` cũ). Cần thêm `AND o.payment_status = 'PAID'` vào JOIN condition + lưu định nghĩa vào file SQL mới để đưa vào source control (hiện chỉ tồn tại trong DB, không ai review được).

**Nợ kỹ thuật phát hiện phụ (chưa xử lý, ngoài phạm vi lần này):**
6. `OrderService.applyVoucherToOrder()` — gọi `userVoucher.getIsUsed()` trước khi kiểm tra `userVoucher != null`, có thể `NullPointerException` khi dùng voucher public chưa có bản ghi `UserVoucher` riêng.

**Cần làm tiếp — hệ thống khuyến mãi đa loại (Giai đoạn 3, xem lịch sử phía trên):**
7. Kiểm tra tay qua trình duyệt thật (không có sẵn mật khẩu admin nên chỉ verify được qua API lần này): giao diện `PromotionOfferBox` (full + compact), badge/dòng chữ đỏ ở `ProductCard`/admin table, `GiftDetailModal`, fix layout ảnh ở `ProductDetail.jsx` khách hàng, và Popover "Bộ lọc" mới ở `Product.jsx` admin — logic tính tiền/validate/filter đã xác nhận đúng qua API thật (kể cả sau khi vá bug số lượng quà tặng + bug filter "Không khuyến mãi"), chỉ còn thiếu bước xác nhận UI bằng mắt.
8. `PromotionExpiryScheduler` (cron mỗi giờ, tự động khôi phục giá khi hết hạn khuyến mãi) chưa test real-time được trong phiên làm việc này — chỉ xác nhận qua code review + build; nên theo dõi log/DB sau khi deploy để chắc chắn job chạy đúng lần đầu.
9. Dữ liệu test còn sót lại trong DB (vô hại, có thể xoá tay qua admin UI nếu muốn): tài khoản `promo_test_verify@example.com` (role USER) và 3 sản phẩm `TEST BOGO Product`/`TEST Bundle Product`/`TEST Discount Product` (đã ẩn `active=false`).
10. Quà tặng "Mua X tặng Y" hiện chỉ là thông tin hiển thị — số lượng tặng chưa được tự động cộng vào `OrderDetail.quantity`/trừ thêm tồn kho khi tạo đơn, nên về mặt vận hành kho, nhân viên đóng gói cần tự biết thêm đúng số lượng quà tặng vào đơn thủ công. Mở rộng để tự động hoá phần này (nếu cần) sẽ đụng đến `OrderService.create()` (tăng `item.getQuantity()` thêm `freeUnits` khi ghi `OrderDetail`+trừ kho) — chưa làm vì ngoài phạm vi yêu cầu lần này.
11. **Cần làm tiếp — verify snapshot khuyến mãi ở trang chi tiết đơn hàng**: đặt 1 đơn hàng MỚI (COD, sản phẩm đang có khuyến mãi `BUY_X_GET_Y` hoặc `BUNDLE_PRICE` active) rồi xác nhận bằng mắt qua trình duyệt: cột "Khuyến mãi" ở admin `OrderDetail.jsx` hiện đúng `Tặng {N}`/`Mua {bundleQty} giá {bundlePrice}đ`; PDF "in hóa đơn" hiện đúng cột khuyến mãi + giá gốc gạch ngang (loại `PRICE_DISCOUNT`); member `History.jsx`/`OrderCard.jsx` hiện khớp y hệt. Toàn bộ mới xác nhận qua build/compile pass, chưa test tay qua UI thật (xem chi tiết ở mục "Snapshot khuyến mãi ở cấp `OrderDetail`..." trong Lịch sử phía trên).

**Chủ động không làm (theo yêu cầu người dùng):**
7. Tab "Đơn hàng chứa sản phẩm" ở `ProductDetail.jsx` admin — backend chưa có endpoint truy vấn `OrderDetail` theo `productId`, cần join `Order`/`OrderDetail` mới nếu muốn làm sau này.
